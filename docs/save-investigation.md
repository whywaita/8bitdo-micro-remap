# Micro save investigation

## Confirmed defect

The save verifier assumes every byte in the 180-byte payload remains equal to the submitted payload. On the tested device, saving a single mapping causes the device to change global offsets 0 and 1 as well. The requested mapping is present in the CRC-valid readback, but the exact comparison raises `VERIFY_FAILED`.

This contradicts the original design's assumption that all bytes outside edited mappings remain unchanged after the device processes a save. Preservation of outgoing unknown bytes remains necessary; device-generated changes require separate investigation. The meaning of offsets 0 and 1 is not established. They are not identified as a checksum. Following the user-authorized investigation, the application accepts their device-generated changes only during post-save/restore comparison while retaining full page CRC validation.

## Observations

Investigation date: 2026-09-09. The user authorized additional device writes for diagnosis. Raw snapshots were kept locally outside Git. The probe validated response framing, page offsets, and CRC, backed up all 180 bytes, checked the fresh baseline before writing, and modified only physical A's mapping. Down was preserved.

| Experiment                                                                                          | Result                                                                        |
| --------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Read through an independent Python/CoreBluetooth client using the web initialization sequence       | A mapped to G and Down to D, matching the official app                        |
| Change only A to keyboard A; wait 600 ms after commit; read four pages                              | A mapped to A; the only unexpected changes were offsets 0 and 1               |
| Disconnect and reconnect; read using web initialization                                             | A remained A, Down remained D                                                 |
| Use the alternative observed initial `04 5a` packet with payload `02` instead of `00`               | The displayed A and Down mappings were unchanged                              |
| Change A to B with the web initialization sequence before reads and no deliberate post-commit delay | A mapped to B; again only offsets 0 and 1 differed from the submitted payload |
| Restore A to the user's requested keyboard A                                                        | Readback A was A; Down remained D; offsets 0 and 1 again changed              |

After the first A write, the user sent `aaa` in response to the request to test physical A. This is consistent with successful input, but the input source was not independently observed. The user subsequently confirmed that the official app also displayed A after the final restoration.

Small save/commit notifications were observed. The application currently awaits GATT write completion but does not interpret these protocol responses. Their status fields have not been decoded, so GATT completion must not be described as a device-level commit acknowledgement.

## Ruled out or weakened hypotheses

- The running local server reports `MODE=development` and uses the real transport, not the E2E fake runtime.
- Reading in the UI clears draft edits before requesting a fresh device snapshot.
- The independent reader uses A offset 12 and Down offset 72, matching both the current implementation and the public references.
- The two observed initial selector payloads did not produce different mappings in this experiment.
- The no-delay experiment did not reproduce a failure to read the requested mapping. A missing delay alone is therefore not an established explanation.

## Still unresolved

The user's earlier web readback of A/Down while the official app and USB reported G/D has not been reproduced under controlled comparison. The independent baseline was G/D. Do not claim that the verifier defect alone explains that discrepancy.

The existing fake transport copies the submitted payload verbatim on commit. It cannot detect device-generated header changes or establish real input behavior. Existing tests passing did not validate these hardware assumptions.

Next evidence needed: independently confirm final A input and the official-app view; determine the semantics of the two device-generated bytes and the device-level save responses before changing the verification invariant. The subsequent application update preserves bytes 0–1 on write and accepts their returned values during post-save/restore verification only. All other 178 bytes must match; stale-baseline checks still require full equality. Regression tests cover both save and restore, actual-header retention, outgoing-header preservation, and mismatches at every offset from 2 through 179.
